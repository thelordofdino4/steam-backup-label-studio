# Local Release Diagnostics

> Status: Proposed core source coverage for #379; integration, native and packaged acceptance remain pending.
> Scope: Extends the existing command/menu/Steam diagnostics with image/discovery, command admission and startup observation. Uses the shared asynchronous-work and image-policy owners. Source tests do not establish native or packaged acceptance.

## Current ownership

The existing application dispatcher remains the sole command execution, authorization, busy-scope and typed-result owner. Its optional execution observer starts only after scope acquisition and sees the original terminal result after scope release. Joined dispatches share one execution and one observation. Observer failures cannot replace business outcomes, publish feedback or retain scopes. Rejected/disabled/unknown dispatch attempts are separate admission records, not executions.

One [application runtime](../src/app/applicationLifecycleRuntime.ts) uses one [bounded diagnostic collector](../src/diagnostics/applicationCommandDiagnostics.ts), created by the production entry point before application composition (or by a standalone runtime when no collector is supplied). It records existing command executions, including Open, Save/Save As, PNG export and available Case preset commands, without storing or mutating a project/session snapshot. Collector-owner disposal clears records; late completions cannot revive cleared or evicted records.

The collector retains 100 records by default, with a hard configurable maximum of 200 shared by commands, admissions, Steam/image/discovery work, application startup/runtime and menu diagnostics. Each record has a sequence, allowlisted identity, running/terminal status and monotonic elapsed milliseconds. Command records include the canonical generated operation ID when available. Elapsed values cap at 24 hours with an explicit cap flag. Snapshots of pending records show current elapsed time without polling or adding a second job scheduler.

Failure codes are copied only from exact known-code sets, including the existing package and project-file registries. Unknown codes are `unclassified`. Package stages reuse the native registry; other known stages come from exact failure-code mappings. The report never copies user messages, diagnostic strings, arbitrary causes, success values, feedback, project/asset bytes, filenames, paths, queries, credentials, custom operation IDs or wall-clock timestamps. It serializes a new allowlisted projection rather than filtering a serialized exception/project after the fact.

The [menu diagnostic contract](../src/applicationMenu/applicationMenuDiagnostics.ts) names native availability, window identity, platform lookup, native event subscription, menu installation, Windows accelerators and lifecycle/window subscription prerequisites. The existing menu runtime start result remains authoritative: `unavailable` is not failure, and `started` means registration/subscriptions completed and initial projection was scheduled, not that every semantic owner or the whole application is ready. Asynchronous projection failures identify window-state capture, capability projection or native apply separately. A pending startup record shows the current prerequisite and elapsed time; no timeout, cancellation or retry policy is introduced.

The [native port](../src/applicationMenu/nativeApplicationMenuPort.ts) supplies stage notifications without wrapping/replacing its original errors. Callback failures cannot change startup, dispatch or native outcomes. Disposing during pending window subscription cleans up its eventual listener without reporting a false startup failure. Default menu console logging prints only allowlisted codes/stages; raw `detail` remains internal to explicitly injected diagnostic callbacks and is never projected into report JSON. There is no global console interception.

`runtime.diagnostics.snapshot()` and `toJson()` expose a local in-memory report API. Report version 4 retains optional `component`/`event` identities for menu entries and adds exact `workflowId` plus safe numeric `requestId` for Steam/image/discovery work, plus an optional exact allowlisted native cause code, while preserving command records. All record kinds share one storage budget. Command `failure` and the menu owner's existing `failed` start result retain their distinct owner vocabulary; an event's `reported` status does not label ordinary duplicate/rejected invocation diagnostics as command failures. The offline Help surface now exposes that report as a read-only, selectable snapshot with explicit Refresh. Home has a Help and local diagnostics button independent of native-menu installation. The existing `menu.help.documentation` routes to `help.open-documentation` through an informational owner; it never dispatches a project command. About stays disabled until its runtime metadata owner exists, and Report an Issue stays omitted. There is no file persistence, clipboard API, telemetry or upload; users explicitly copy selected text with their normal keyboard command.

The [Help hook](../src/app/useApplicationHelp.tsx) owns capability checks, report capture, safe feedback and focus, while the [panel](../src/help/ApplicationHelpPanel.tsx) remains presentational and the [packaged resource](../src/help/applicationHelpResource.ts) derives its introductory copy from reviewed project documentation. This nonmodal panel uses the existing workflow-host presentation styles. Opening Help closes the current Tools presentation; invoking Tools dismisses Help before the existing navigation owner focuses its target. Existing application/native dialog phases prevent Help activation, including a fresh recheck for a stale native enabled state. Opening or refreshing Help neither changes project/session state nor captures another project snapshot. Open/refresh failures retain safe copy; report refresh failures preserve the previous report. Close/Escape returns focus to a surviving opener or the registered current workspace/Home fallback; a remounted Help presentation focuses its heading.

The entry point creates the report owner before dynamically loading application composition. A plain DOM fallback exposes a captured report even if module loading, the mount root, lifecycle/menu construction or React rendering fails. Native failures before a WebView exists use a separate static native startup report described below. Headless component diagnostics are source evidence, not native keyboard, screen-reader, clipboard or packaged visual acceptance.

PNG export continues returning its existing `export.<stage>-failed` typed codes and internal provenance. Its user/feedback messages now identify the failed stage and an action without interpolating raw platform exception text.

## Steam workflow observation

The existing [Steam hook](../src/hooks/useSteamImport.ts) retains the #304 query-generation owner and #367 session/revision request authority. The [Steam diagnostic adapter](../src/steam/steamWorkflowDiagnostics.ts) reuses `ApplicationCommandError` and `ApplicationCommandResult` for safe failure copy/outcomes; it does not register a second command or scheduler. Search and import observations retain only an allowlisted workflow name, a positive safe-integer request ID, a known stage, elapsed time and projected outcome. Queries, App IDs, game titles, native messages, causes, project/session identities and payloads are not copied into reports.

Import reports success only after the existing checked commit returns true. Current failures publish safe copy through the existing checked feedback completion, including synchronous application failures. A retired search/import records `cancelled` and cannot replace current UI status or become a success. Here cancellation means acceptance authority was retired; it does not claim the native transport was aborted. Pending records show elapsed time until transport/preparation completes, including work whose authority was retired meanwhile. Diagnostics do not extend that authority. The existing async boundary still is not an arbitrary-setter rollback transaction; #366 remains a separate gate.

`fetch-and-normalize` deliberately includes native fetch plus response normalization; finer transport/parse attribution is not yet available at this owner. `prepare` includes artwork/metadata preparation, and `apply` is the existing synchronous checked callback. Optional enrichment failures swallowed by existing domain fallback policy are not falsely reported as whole-import failures. Optional thumbnail caches remain UI-only best-effort work; they do not acquire project mutation authority.

## Image and discovery observation

`ProjectAsyncWork` now accepts an optional observer. The existing begin/commit/publish/retirement paths remain the only authority. `fail` is a typed failure completion through the same exact-once feedback gate; it cannot restore a failed or stale request. Optional typed outcomes on proposal/commit completion let discovery retain usable candidates while recording a partial provider failure. Observer exceptions never replace an owner result or extend mutation authority. Steam game work and derived Case branding reconciliation are excluded from this observer to avoid duplicate or misleading import records.

Reports map destination lanes to fixed workflow categories (`image.import`, metadata/artwork/logo/screenshot discovery); user-created slot suffixes and session identities are never copied. Supersession, invalidation, navigation, competing mutation and disposal end the observation as cancelled when retirement is observed. This measures acceptance lifetime, not guaranteed transport cancellation. Late work cannot revive an observation. Synchronous application failure records the apply stage before its one permitted safe feedback completion.

The shared image importer retains existing #358 validation and unchanged encoded bytes. File reads, native policy validation, browser decoding and active-pixel inspection retain typed provenance through the existing application error shape. The native codec's exact known code/stage may be projected as provenance; its messages, paths and content never enter report JSON. Existing policy conversion guidance remains actionable. No decoder, conversion fallback, image budget or package limit is replaced. Unknown upstream acquisition failures use the honest coarse prepare stage.

Disc background/title/additional artwork/logos/marks/banner, local screenshots, remote candidates, Case cover/tray/left/right images and Case logos/banners use the existing checked completion. Case loaders optionally pass typed failures to that owner before returning null; a failed load cannot consume mutation authority as a successful image. Failed replacement keeps previously accepted image/selection. Discovery UI replaces arbitrary exception strings with fixed recovery copy; optional provider errors retain usable candidates and record `discovery.provider-failed`, without provider URLs or user metadata.

Additional tests cover throwing observers, exact-once failure completion, partial provider results, cancellation timing, safe native provenance, all nine representative mounted image destinations, and preserving accepted images on current read failure. This is source validation only; Windows WebView image validation, menu/Help copy, drag/preview/export/save parity and packaged failure injection remain native acceptance gates.

## Composition, render and native startup failures

`main.tsx` owns the collector before dynamically importing `bootstrapApplication.tsx`. The bootstrap still constructs the same lifecycle/menu owners and mounts the same application boundary tree. Named prerequisites are the document root, application module, lifecycle root, menu runtime, React root and React render. `ApplicationRendered` records only the first committed React tree; it does not claim menu installation, every semantic owner, image loading or whole-workflow readiness. Menu readiness remains separately observed. Later caught/recoverable React failures receive separate runtime events; an uncaught render failure opens the fallback.

An externally supplied collector remains owned by the entry point, so lifecycle cleanup cannot erase the startup failure before capture. The failure path captures only the allowlisted report, cleans up the runtime and renders a plain DOM heading, safe guidance and read-only selectable report. It performs no automatic reload, file write, clipboard API call or network delivery. The fallback uses text nodes/value assignment, not HTML interpolation. Native keyboard/focus acceptance remains required. JavaScript execution that never reaches the entry point, OS termination and process crashes cannot be guaranteed to produce an in-app report.

`src-tauri/src/startup_diagnostics.rs` classifies returned Tauri startup errors by native window/WebView, plugin, setup, packaged asset, icon or unknown startup prerequisite. It never formats a platform error or plugin/path payload. A bounded monotonic elapsed time and static recovery copy are printed to stderr. Windows also presents the same report in a native message box independent of WebView construction (Ctrl+C uses the normal Windows dialog copy behavior). Existing `windows-sys` supplies this UI call; no new package, persistent log or service is introduced. The app exits with failure status after reporting a returned startup error. Rust tests exercise only pure projection, not a native dialog. Linux/macOS stderr delivery and Windows dialog/runtime integration still need packaged acceptance.

Command admission observations cover command lookup, capability evaluation, repeat-key calculation and busy-scope acquisition. They preserve exact existing results, never acquire scopes themselves, never duplicate joined executions and omit arbitrary command IDs/messages/input. Refusal is recorded as `not-executed`, distinct from an executed failure. Export snapshot failure and legal clipboard failure now also use safe recovery copy; internal typed export causes remain available to their existing owner.
