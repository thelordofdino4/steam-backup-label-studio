# Local Release Diagnostics

> Status: CURRENT source checkpoint for the command-observation, menu-readiness, offline Help/report and Steam workflow slices of #379; TARGET for remaining workflow, startup and packaged acceptance.
> Baseline: diagnostics extend the existing command and async-request owners; project/schema and native acceptance requirements remain independent.

## Current ownership

The existing application dispatcher remains the sole command execution, authorization, busy-scope and typed-result owner. Its optional execution observer starts only after scope acquisition and sees the original terminal result after scope release. Joined dispatches share one execution and one observation. Observer failures cannot replace business outcomes, publish feedback or retain scopes. Rejected/disabled/unknown dispatch attempts are not execution records.

One [application runtime](../src/app/applicationLifecycleRuntime.ts) owns one [bounded diagnostic collector](../src/diagnostics/applicationCommandDiagnostics.ts). It records existing command executions, including Open, Save/Save As, PNG export and available Case preset commands, without storing or mutating a project/session snapshot. Disposal clears records; late completions cannot revive cleared or evicted records.

The collector retains 100 records by default, with a hard configurable maximum of 200 shared by commands, menu startup and menu diagnostics. Each record has a sequence, allowlisted identity, running/terminal status and monotonic elapsed milliseconds. Command records include the canonical generated operation ID when available. Elapsed values cap at 24 hours with an explicit cap flag. Snapshots of pending records show current elapsed time without polling or adding a second job scheduler.

Failure codes are copied only from exact known-code sets, including the existing package and project-file registries. Unknown codes are `unclassified`. Package stages reuse the native registry; other known stages come from exact failure-code mappings. The report never copies user messages, diagnostic strings, arbitrary causes, success values, feedback, project/asset bytes, filenames, paths, queries, credentials, custom operation IDs or wall-clock timestamps. It serializes a new allowlisted projection rather than filtering a serialized exception/project after the fact.

The [menu diagnostic contract](../src/applicationMenu/applicationMenuDiagnostics.ts) names native availability, window identity, platform lookup, native event subscription, menu installation, Windows accelerators and lifecycle/window subscription prerequisites. The existing menu runtime start result remains authoritative: `unavailable` is not failure, and `started` means registration/subscriptions completed and initial projection was scheduled, not that every semantic owner or the whole application is ready. Asynchronous projection failures identify window-state capture, capability projection or native apply separately. A pending startup record shows the current prerequisite and elapsed time; no timeout, cancellation or retry policy is introduced.

The [native port](../src/applicationMenu/nativeApplicationMenuPort.ts) supplies stage notifications without wrapping/replacing its original errors. Callback failures cannot change startup, dispatch or native outcomes. Disposing during pending window subscription cleans up its eventual listener without reporting a false startup failure. Default menu console logging prints only allowlisted codes/stages; raw `detail` remains internal to explicitly injected diagnostic callbacks and is never projected into report JSON. There is no global console interception.

`runtime.diagnostics.snapshot()` and `toJson()` expose a local in-memory report API. Report version 3 retains optional `component`/`event` identities for menu entries and adds exact `workflowId` plus safe numeric `requestId` for Steam work, while preserving command records. All record kinds share one storage budget. Command `failure` and the menu owner's existing `failed` start result retain their distinct owner vocabulary; an event's `reported` status does not label ordinary duplicate/rejected invocation diagnostics as command failures. The offline Help surface now exposes that report as a read-only, selectable snapshot with explicit Refresh. Home has a Help and local diagnostics button independent of native-menu installation. The existing `menu.help.documentation` routes to `help.open-documentation` through an informational owner; it never dispatches a project command. About stays disabled until its runtime metadata owner exists, and Report an Issue stays omitted. There is no file persistence, clipboard API, telemetry or upload; users explicitly copy selected text with their normal keyboard command.

The [Help hook](../src/app/useApplicationHelp.tsx) owns capability checks, report capture, safe feedback and focus, while the [panel](../src/help/ApplicationHelpPanel.tsx) remains presentational and the [packaged resource](../src/help/applicationHelpResource.ts) derives its introductory copy from reviewed project documentation. This nonmodal panel uses the existing workflow-host presentation styles. Opening Help closes the current Tools presentation; invoking Tools dismisses Help before the existing navigation owner focuses its target. Existing application/native dialog phases prevent Help activation, including a fresh recheck for a stale native enabled state. Opening or refreshing Help neither changes project/session state nor captures another project snapshot. Open/refresh failures retain safe copy; report refresh failures preserve the previous report. Close/Escape returns focus to a surviving opener or the registered current workspace/Home fallback; a remounted Help presentation focuses its heading.

The report is available only after React/application construction succeeds. Pre-WebView/native-process startup, missing mount roots and lifecycle-construction failures still need a separate prerequisite/fallback path through their existing owners. Headless component diagnostics are source evidence, not native keyboard, screen-reader, clipboard or packaged visual acceptance.

PNG export continues returning its existing `export.<stage>-failed` typed codes and internal provenance. Its user/feedback messages now identify the failed stage and an action without interpolating raw platform exception text.

## Steam workflow observation

The existing [Steam hook](../src/hooks/useSteamImport.ts) retains the #304 query-generation owner and #367 session/revision request authority. The [Steam diagnostic adapter](../src/steam/steamWorkflowDiagnostics.ts) reuses `ApplicationCommandError` and `ApplicationCommandResult` for safe failure copy/outcomes; it does not register a second command or scheduler. Search and import observations retain only an allowlisted workflow name, a positive safe-integer request ID, a known stage, elapsed time and projected outcome. Queries, App IDs, game titles, native messages, causes, project/session identities and payloads are not copied into reports.

Import reports success only after the existing checked commit returns true. Current failures publish safe copy through the existing checked feedback completion, including synchronous application failures. A retired search/import records `cancelled` and cannot replace current UI status or become a success. Here cancellation means acceptance authority was retired; it does not claim the native transport was aborted. Pending records show elapsed time until transport/preparation completes, including work whose authority was retired meanwhile. Diagnostics do not extend that authority. The existing async boundary still is not an arbitrary-setter rollback transaction; #366 remains a separate gate.

`fetch-and-normalize` deliberately includes native fetch plus response normalization; finer transport/parse attribution is not yet available at this owner. `prepare` includes artwork/metadata preparation, and `apply` is the existing synchronous checked callback. Optional enrichment failures swallowed by existing domain fallback policy are not falsely reported as whole-import failures. Other discovery/image hooks still need coverage and safe-copy reconciliation.
